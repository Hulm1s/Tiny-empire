# CHARACTERS AND MODELS

Everything about the villagers: where the models come from, how the Blender pipeline works, how
to change a character, and what breaks one.

---

## 1. The headline facts

1. **There are no character prefabs.** Nothing is a `.prefab` asset. Characters are FBX model
   prefabs, instantiated and assembled by **editor-only** code at scene-build time.
2. **All character assembly code is editor-only.** `CharacterLibrary.cs` and
   `CharacterImportSettings.cs` live in `Assets/_Project/Editor/`. **The only runtime character
   script in the whole project is `CharacterVisual.cs` (85 lines).** Nothing can spawn a villager
   at runtime — customers are clones of an inactive template the scene build already placed.
3. **The rig is Generic, not Humanoid.** One skeleton, 20 bones, shared by every role.
4. **One animator controller, four clips**, shared by everyone, and it is **deleted and rebuilt
   from scratch on every `Spawn` call**.
5. **Hats are part of the skinned mesh**, joined in Blender and weighted 100% to the `Head` bone.
   There is no accessory-attachment system in Unity.
6. **The models are generated by Python scripts driving Blender 2.93.2**, from one purchased GLB.

## 3. The full chain, source → character on screen

| # | Step | Entry point | Produces |
|---|---|---|---|
| 1 | purchased GLB | `models/low+poly+humanoid+3d+model.glb` | — |
| 2 | voxel remesh → QuadriFlow retopo → triangulate → flat shade → scale to 1.5 m → **measure joints off the mesh** → 20-bone armature → auto weights | `rig.py` | `humanoid_rigged.blend` + `rig_testpose.png` |
| 3 | keyframe 4 actions, add cyclic modifiers, assign 4 material slots per-face by body region | `animate.py` | `humanoid_animated.blend` |
| 4 | copy the body ×4, recolour, build + join + head-weight a hat, clear the pose, export 5 FBXs | `export_unity.py` | the 5 FBXs in `Art/Characters/` |
| 5 | Unity import forced by an `AssetPostprocessor`: flat normals, Generic rig, avatar copy, clip rename + loop, URP material creation | `CharacterImportSettings.cs` | model prefabs, `Villager_RigAvatar`, 4 clips, 22 `.mat` |
| 6 | animator controller built from code: 4 states, 4 Any-State transitions on one int | `CharacterLibrary.EnsureController()` | `Villager.controller` |
| 7 | scene build instantiates each FBX as a prefab instance, adds `Animator` + `CharacterVisual`, tints a slot | `CharacterLibrary.Spawn()` | `Farm.unity` |
| 8 | at runtime, `CharacterVisual` measures its own speed and reads `CarryStack.Count`, sets `State` | `CharacterVisual.cs` | the animator picks a clip |

### ⚠ The role is chosen from the hire's display label

`FarmSceneBuilder.cs:581-583`:

string model = role.StartsWith("Cashier") || role.StartsWith("Milk")

## 5. The rig

**Generic, not Humanoid.** Set in code, `CharacterImportSettings.cs:52`:

```csharp
importer.animationType = ModelImporterAnimationType.Generic;
```

The reason: the proportions are stylised, Unity's humanoid retargeter would fight them, and all
roles share one skeleton so there is nothing to retarget.

### The skeleton — 20 bones, exact names

```
Villager_Farmer            <- prefab root (named after the file)
├── Farmer                 <- the SkinnedMeshRenderer (named after the role)
└── Rig                    <- armature
    └── Root
        └── Hips
            ├── Spine → Chest → Neck → Head
            ├── Chest → Shoulder.L → UpperArm.L → Forearm.L → Hand.L
            ├── Chest → Shoulder.R → UpperArm.R → Forearm.R → Hand.R
            ├── Thigh.L → Shin.L → Foot.L
            └── Thigh.R → Shin.R → Foot.R
```

**These names and this path structure are a hard dependency.** The clips bind by transform path
(e.g. `Rig/Root/Hips/Thigh.L`), which is why `optimizeGameObjects` is `0` — the bone hierarchy
must stay real.

Per-role: Owner 3676 tris / 6 materials / 20 bones, Farmer 3680 / 6 / 20, Cashier 3744 / 6 / 20,
Customer 3572 / **4** / 20.

### Import settings (identical across all five)

`globalScale 1`, `useFileScale 1`, `meshCompression Medium`, `normalSmoothAngle 1` +
`normalCalculationMode 4` (forces the flat-shaded look regardless of exported smoothing),
`importTangents None`, `optimizeGameObjects 0`, `optimizeBones 1`, `maxBonesPerVertex 4`,
`isReadable 0`.

## 6. ⚠ The avatar — the single most fragile thing here

The avatar is a **sub-asset of `Villager_Rig.fbx`** called `Villager_RigAvatar`. The four role
FBXs are supposed to copy it (`avatarSetup: 2`, `CopyFromOther`).

**Verified state of the committed `.meta` files:**

| File | `animationType` | `avatarSetup` | Meaning |
|---|---|---|---|
| `Villager_Rig.fbx` | 2 (Generic) | **1** | CreateFromThisModel ✅ |
| `Villager_Farmer.fbx` | 2 | **2** | CopyFromOther ✅ |
| `Villager_Cashier.fbx` | 2 | **0** | ⚠ NoAvatar |
| `Villager_Customer.fbx` | 2 | **0** | ⚠ NoAvatar |
| `Villager_Owner.fbx` | 2 | **0** | ⚠ NoAvatar |

### Why this happens

`CharacterImportSettings.OnPreprocessModel` can only set `CopyFromOther` if `Villager_Rig.fbx`
has already imported. On a fresh clone the roles can import first and fall through to `NoAvatar`.
The last `Tycoon → Verify Character Models` run reported all four as
`avatarSetup=CopyFromOther source=set`, so the force-reimport does fix it in-session — but the
`.meta` on disk was never re-serialised to match.

Compounding it: `FarmSceneBuilder.Build()` **never calls `CharacterLibrary.ReimportRoles()`**,
despite that method's own doc comment saying it runs "once at the start of a scene build". So the
scene is built against whatever import state the editor happens to hold.

### Does it actually break animation? — **UNKNOWN / NEEDS MANUAL VERIFICATION**

A Generic `Animator` with a null avatar *can* still bind generic clips by transform path, and the
paths do match exactly. The last web build logged `BUILD_OK` with no animator warnings. But the
project's own README states flatly that no avatar means no movement.

**If villagers are standing still in the game, this is the first thing to check.** The fix is:

```
Tycoon → Reimport Character Models        (CharacterLibrary.ReimportRoles)
Tycoon → Verify Character Models          (CharacterLibrary.Verify)
```

Every role must report `avatarSetup=CopyFromOther source=set`, `bones=20`, and the controller
must report `states=4`. Then rebuild the scene.

## 7. Animation

**Four clips, all embedded in `Villager_Rig.fbx` only.** Nothing else in the project contains an
`AnimationClip`.

| Clip | Frames | Length | Loops |
|---|---|---|---|
| `Idle` | 0 → 89 | 3.71 s | yes |
| `Walk` | 0 → 24 | 1.00 s | yes |
| `CarryIdle` | 0 → 89 | 3.71 s | yes |
| `CarryWalk` | 0 → 24 | 1.00 s | yes |

Blender writes the takes as `Rig|Idle` etc. `CharacterImportSettings.OnPreprocessAnimation()`
strips everything up to the last `|` and sets `loopTime = true`.

**⚠ That hook is gated on the literal filename `"Villager_Rig.fbx"`.** A rig exported under any
other name gets neither renamed clips nor looping — which looks exactly like a broken rig.

Each clip has 210 curve bindings over 21 transform paths. The FBX also carries four
`__preview__Rig|*` artefacts, which the diagnostics skip by prefix.

### The controller

`Villager.controller` is **deleted and rebuilt from scratch on every single `Spawn` call** — 11
times per scene build, each logging `[CharacterLibrary] Animator rebuilt: 4 states wired.`

This is deliberate. An earlier version cached it, and a controller once stayed wired to clip names
that no longer existed — nothing looked wrong until you were in game watching nobody move.

Structure: one int parameter `State`, four states, four Any-State transitions with
`State Equals i`, `hasExitTime = false`, `duration = 0.12`, default state `Idle`.

If fewer than four clips are found it logs:
`Only {n}/4 states got a clip. Characters will stand still. Re-export the rig from Blender.`

### What drives it at runtime

`CharacterVisual.cs` — a **watcher, not a controller**:

```csharp
enum Motion { Idle = 0, Walk = 1, CarryIdle = 2, CarryWalk = 3 }
```

- Re-evaluates every `0.1 s`, with the first evaluation randomly staggered so a crowd does not
  all re-evaluate on one frame.
- `speed = Δposition / elapsed`, smoothed with `Lerp(_smoothedSpeed, speed, 0.6f)` — *"or a
  character stopping for one sample flickers between clips."*
- `moving = _smoothedSpeed > walkThreshold` (**0.25 m/s**)
- `loaded = carry != null && carry.Count > 0`

> Deliberately a watcher, not a controller [...] That means the player, workers and customers all
> animate correctly without a single line changing in PlayerMotor, WorkerAgent or CustomerAgent.

**`PlayerMotor`, `WorkerAgent` and `CustomerAgent` contain zero animator code.**

Two settings that exist because of real failures:
- `Animator.cullingMode = AlwaysAnimate` — *"Culling depends on the skinned renderer's bounds
  being right, and when they are not the character simply freezes - a saving worth far less than
  a farm full of statues."*
- `SkinnedMeshRenderer.updateWhenOffscreen = true` — *"the bind-pose bounds are wrong once a
  character raises its arms, and wrong bounds make it vanish at the edges."*

## 8. How the four roles differ

Each role is its **own FBX** with its own copy of the identical mesh (plus a joined hat) and its
own material set. The skeleton and the clips are **not** duplicated.

### Material slot order — fixed, and hardcoded

`CharacterLibrary.cs:28`:
```csharp
public const int ShoeSlot = 0, TrouserSlot = 1, ShirtSlot = 2, SkinSlot = 3;
```
Slot 4 = Hat, slot 5 = HatTrim (no named constants).

| Slot | Owner | Farmer | Cashier | Customer |
|---|---|---|---|---|
| 0 Shoe | `Owner_Shoe` 58,44,36 | `Farmer_Shoe` 92,62,38 | `Cashier_Shoe` 70,52,44 | `Customer_Shoe` 88,62,50 |
| 1 Trouser | `Owner_Trouser` 44,52,74 | `Farmer_Trouser` 140,104,60 | `Cashier_Trouser` 70,74,86 | `Customer_Trouser` 150,132,112 |
| 2 Shirt | `Owner_Shirt` 238,232,218 | `Farmer_Shirt` 52,120,210 | `Cashier_Shirt` 46,168,116 | `Customer_Shirt` 214,92,72 |
| 3 Skin | `Owner_Skin` 234,182,142 | `Farmer_Skin` 232,180,140 | `Cashier_Skin` 228,174,134 | `Customer_Skin` 240,190,150 |
| 4 Hat | `Owner_Hat` 176,58,46 (flat cap) | `Farmer_Hat` 214,178,96 (straw hat) | `Cashier_Hat` 46,82,150 (ball cap) | — none |
| 5 HatTrim | `Owner_HatTrim` 140,42,34 | `Farmer_HatTrim` 150,110,58 | `Cashier_HatTrim` 210,214,220 | — none |

Values are 0-255 sRGB from `export_unity.py:87-98`.

**⚠ Customer has 4 slots; the others have 6.** Any code indexing slots 4 or 5 must not be handed
a Customer.

The player is the `Owner` — white shirt and a red cap, *"so the one character the player actually
controls is never confused with the staff or the shoppers."*

### Two layers of recolouring on top

- **Workers** are tinted at **scene-build time** by `CharacterLibrary.Tint(model, ShirtSlot,
  color)`. This `new Material(...)`-copies slot 2, so the result is **8 Material objects embedded
  inside `Farm.unity`** — not assets.
  **⚠ Editing `Materials/Characters/Farmer_Shirt.mat` will NOT change a worker's shirt.** Only a
  scene rebuild will. (The README's "just edit the .mat" advice is correct for every other slot
  and silently wrong for this one.)
- **Customers** are tinted at **runtime** by `CustomerAgent.Begin()` using a
  `MaterialPropertyBlock` on slot 2.

## 9. "I have a brand-new FBX/GLB humanoid. What do I do?"

There are two honest routes.

### Route A — through the existing pipeline (what the architecture expects)

The whole design rests on *one* skeleton with *these* bone names, so the cheapest correct path is
to re-derive a rig rather than import a foreign one.

1. Put the source in `D:\iosGame\models\`. (`rig.py` imports GLB; for an FBX source, change the
   one `bpy.ops.import_scene.gltf` line to `bpy.ops.import_scene.fbx`.)
2. Run `rig.py`:
   ```bash
   "D:\Blender\blender.exe" --background --python "D:\iosGame\models\pipeline\rig.py" -- "D:\iosGame\models\<your>.glb" "D:\iosGame\models\pipeline" <FACES>
   ```
   ⚠ The `FACES` value used for the shipped models is **UNKNOWN** — it is recorded nowhere. The
   roles land at 3572–3744 tris after the hat join, so aim for that region.
   Watch for `MEASURED …`, `RIG bones=…`, `WEIGHTS ok (automatic)`, `RIG_OK`.
   `WEIGHTS_FAILED` means auto-weighting fell over.
3. Look at `rig_testpose.png` — that render exists purely to prove the mesh deforms.
4. **If the new body is not 1.5 m tall**, fix `HEIGHT` in `rig.py:14` *and* the hardcoded metre
   thresholds in `animate.py:149-159` and `export_unity.py:26`. See §10.
5. Run `animate.py`:
   ```bash
   "D:\Blender\blender.exe" --background --python "D:\iosGame\models\pipeline\animate.py" -- "D:\iosGame\models\pipeline\humanoid_rigged.blend" "D:\iosGame\models\pipeline"
   ```
   Check the printed `REGIONS shoe=… trouser=… shirt=… skin=…` — a zero in any of the four means
   the region thresholds no longer match the body.
6. Run `export_unity.py`:
   ```bash
   "D:\Blender\blender.exe" --background --python "D:\iosGame\models\pipeline\export_unity.py" -- "D:\iosGame\models\pipeline\humanoid_animated.blend" "D:\iosGame\game\Assets\_Project\Art\Characters"
   ```
7. In Unity: `Tycoon → Reimport Character Models`, then `Tycoon → Verify Character Models`.
   Every role must read `avatarSetup=CopyFromOther source=set`, `bones=20`, controller `states=4`.
8. `Tycoon → Diagnose Character Animation` — confirm `drivesLegs=True` on all four clips.
9. Rebuild the scene, then run the layout audit.

### Route B — drop a foreign rigged FBX in directly

Only viable if its skeleton is **bone-for-bone identical**. Hard requirements:

- Named `Villager_<Role>.fbx`, in `Assets/_Project/Art/Characters/`. `CharacterLibrary.Model()`
  builds that path and nothing else resolves it.
- Exactly the transform names and paths in §5. Any renaming (including Unity's dot↔underscore
  substitution) breaks the binding and leaves the character standing still **with no error**.
- Material slots in exactly the order Shoe, Trouser, Shirt, Skin (+ Hat, HatTrim).
- Headwear **joined into the skinned mesh and weighted 100% to `Head`**, not a child object.
- ~1.5 m tall at `globalScale 1`, standing on y=0, facing Unity +Z.
- A `Villager_Rig.fbx` in the same folder with the four takes named `*|Idle`, `*|Walk`,
  `*|CarryIdle`, `*|CarryWalk`.

Then: add `public const string <Role> = "<Role>";` to `CharacterLibrary.cs`; add it to the
`new[] { Owner, Farmer, Cashier, Customer }` arrays in **both** `ReimportRoles()` **and**
`Verify()` (hand-maintained literals); call `CharacterLibrary.Spawn(...)`; reimport, verify,
diagnose, rebuild, audit.

**No new controller and no new clips are ever needed.** That is the whole point of the design.

## 11. What breaks a character

### Named-bone and transform-path dependencies
- `export_unity.py:139` looks up the vertex group **`"Head"`** by exact string. Rename the head
  bone and **the hat silently stops following the head.**
- `animate.py` addresses bones by literal name and **silently `continue`s on a missing one** —
  rename a bone and the clip exports with that limb simply not animated, no error.
- Clips bind by transform path. The role FBX must reproduce the whole path.

### Material slot indices
- Reorder the slots on either side and workers get recoloured boots.
- `CharacterLibrary.Tint()` bounds-checks (silent no-op on a bad index).
  **`CustomerAgent.SetPropertyBlock(block, 2)` does not.**
- `OnAssignMaterialModel` short-circuits on an existing `.mat`, so recolouring in Blender and
  re-exporting **appears to do nothing** until you delete the stale `.mat`.

### Magenta characters
A character rendering magenta means a material that is not a URP material. Delete it from
`Materials/Characters/` and reimport — the postprocessor recreates it correctly. The whole
`OnAssignMaterialModel` hook exists because of this.

### Clip wiring
If `OnPreprocessAnimation` did not strip the `Rig|` prefix, every state gets a null motion, which
looks exactly like a broken rig. The hook is gated on the literal filename `"Villager_Rig.fbx"`.

### ⚠ Hardcoded metres for a 1.5 m body
- `animate.py:145-159` `region_of()`: `0.30`, `0.44`, `0.74`, `0.13`, `0.70`, `1.16`
- `export_unity.py:26`: `head_verts = [v for v in base.data.vertices if v.co.z > 1.14]` — with a
  shorter body this list is **empty**, and the next line is a **ZeroDivisionError**.
- `rig.py:14` `HEIGHT = 1.5`

**Change the character's height in one place and two others break.**

### ⚠ Blender version
The scripts target **2.93.2** and will fail on 4.x:
- `inputs["Specular"]` on Principled BSDF (renamed "Specular IOR Level" in 4.0)
- `scene.render.engine = 'BLENDER_EEVEE'` (`BLENDER_EEVEE_NEXT` in 4.2+)
- `bpy.ops.object.quadriflow_remesh`

## 12. Non-obvious things worth knowing

1. **`Villager_Rig.fbx` is never instantiated** — yet it ships the full `Customer` body mesh and
   its four materials, because `export_unity.py:166` selects `built["Customer"][0]` alongside the
   rig. At 911 KB it is the biggest character file in the project and most of it is redundant.
2. **`roles.py` is dead but still committed**, and `preview_roles.py` only works against *its*
   output (it looks up `Body_Farmer`; `export_unity.py` names the objects plain `Farmer`). Running
   `preview_roles.py` on `humanoid_animated.blend` raises `KeyError`.
3. **`rig.py`'s invocation is undocumented** — the README gives command lines for `animate.py` and
   `export_unity.py` only, and the `FACES` value used for the shipped meshes is lost.
4. **`export_unity.py` clears the rig's action and pose before exporting.** Without it, the last
   action built was `CarryIdle`, so every villager shipped with its arms raised — and with the
   animator briefly playing nothing, that pose was all you ever saw.
5. **`CharacterVisual` measures its own `transform.position` — and its parent `Visual` bobs**
   vertically (±0.07 worker, ±0.06 customer). That motion is part of the speed measured against
   `walkThreshold = 0.25`. It works because of the 0.6 smoothing, but it is a real coupling
   between two systems that look independent.
6. **Customers have no `CarryStack`,** so `CarryIdle`/`CarryWalk` are unreachable for them by
   construction, not by a check.
7. **Facing lives on the root, not the visual.** The `Visual` child is never rotated. This is why
   the export's `axis_forward='-Z', axis_up='Y'` matters: it decides which way the mesh faces
   inside its own local space, once, forever.
8. **`srgb()` appears three times** in the pipeline scripts. Blender's Base Color is a linear
   input; typing sRGB numbers straight in silently washes every colour out.
9. **`CharacterLibrary.cs:62-65` deliberately avoids `??`** on a Unity component — a missing
   component compares equal to null through the overloaded operator but is not actually null, so
   `??` hands back the dead one.
10. **The archived batch logs are genuine ground truth** and are not gitignored:
    `build-verify.log` (per-role avatar/tris/materials/bones), `build-diag.log` (controller
    states, per-clip curve and bone dumps, the full Farmer hierarchy). Re-run
    `CharacterLibrary.Verify` / `CharacterDiagnostics.Run` headlessly rather than guessing.
11. **The measurement heuristics in `rig.py` carry hard-won comments.** Shoulders are found by
    looking for geometry far out to the side rather than by overall width, because the arms hang
    down and the figure is widest at the elbows — a width test drops the shoulder joint halfway
    down the upper arm and makes the walk swing from the elbows. Read them before touching them.

## 13. The diagnostic tools

| Menu item | Method | What it prints |
|---|---|---|
| `Tycoon → Reimport Character Models` | `CharacterLibrary.ReimportRoles` | force-reimports the rig first, then each role, then rebuilds the controller |
| `Tycoon → Verify Character Models` | `CharacterLibrary.Verify` | rig avatar name + validity, every clip's length and loop flag, per role `avatarSetup` / source / tris / materials / bones, controller state count. Logs `VERIFY_OK` |
| `Tycoon → Diagnose Character Animation` | `CharacterDiagnostics.Run` | controller default state, every state's motion (or `NULL`), every Any-State condition, per clip the curve count and bound bone names, `drivesLegs`, then the full `Villager_Farmer` hierarchy. Logs `DIAG_OK` |
